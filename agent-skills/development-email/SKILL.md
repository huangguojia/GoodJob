# 开发信撰写

一封开发信不是「套模板填空」。它是**一次有依据的、针对具体人的商业沟通**。
本 Skill 规定：没有依据不写信；阶段不对不写信；不知道对谁说话就不写信。

## 适用目标

为某一家具体客户（客户 / 线索 / 搜客候选）生成**这一封**该发的开发信草稿，并交付给业务员确认后发送。

## 硬性顺序（不得跳步、不得颠倒）

### 第 0 步 · 先确认「我是谁」

- 读公司资料 `GET /api/company-profile`（公司名称、主营产品、官网）。
- 读个人发件配置（发件邮箱、发件人名称、签名、SMTP）。
- **任一缺失就先补齐，不要开始写信**：公司名称 / 主营产品 / 官网缺失时，后端 `readiness.companyReady=false`，
  发送接口会直接拒绝（`公司资料未完整`）。缺发件配置时连草稿都发不出去。
- 系统检测到缺失会在草稿响应的 `brief.missing` 里列出来，必须先处理。

### 第 1 步 · 先背调，再写信（本 Skill 的核心）

**没有背调就不写开发信。** 顺序永远是「背调 → 写信」，不是「写信 → 补背调」。

- 取这家客户最近一次背调：服务端在生成草稿时自动读取 `background_research_records` 的最新一条。
- 没有背调记录时，先跑一次：`POST /api/ai-background-research { entityType, entityId }`。
  它会联网做四路角度深挖，产出 `facts`（带来源的事实）、`opportunities`（机会判断）、
  `talkTracks`（话术线索）、`risks`（风险）、`verdict`（结论）、`score`（匹配度）。
- **背调只能作为「写什么的依据」，不得把它整段抄进信里**。信里只出现与对方业务直接相关的 1–2 点。

### 第 2 步 · 判定这家客户处在哪个开发阶段

- 取 `GET /api/outreach-journey?entityType=&entityId=` 的 `stage`（阶段是推导值，由触达轨迹算出，不落库）。
- 阶段决定**这封信的唯一目标**，同一家客户在不同阶段的信完全不同：

| 阶段 | 这封信要达成什么 | 关键约束 |
| --- | --- | --- |
| `not_contacted` 未接触 | 换来「愿意看一眼资料」的许可 | 不堆参数、不报价；问题式收尾 |
| `first_touch_sent` 已发首触 | 用一条**首封没给过的新信息**重新赢得注意力 | 不重复首封、不质问为何不回；给退出选项 |
| `following_up` 跟进中 | 收尾式提醒，明确「再没回音就归档」 | 只重申，不再上卖点；请对方一句话确认 |
| `replied_interested` 已回复·可推进 | 把兴趣转成明确需求 | 先逐条回应客户的问题，再索取规格/目标价 |
| `replied_negative` 明确拒绝 | **不发送** | 任何继续投递都违反外发合规约束 |
| `bounced` 退信 | **先换有效邮箱** | 同一地址重发必然再失败 |
| `converted` 已转线索/客户 | 轻量 check-in | 不再走开发信节奏 |

- `replied_negative` / `bounced` 阶段后端会直接拒绝生成（`stage.canSend=false`），不要绕过。

### 第 3 步 · 确定收件人的角色与决策权

- 从联系人姓名、邮箱前缀、背调事实里判断对方是决策人 / 采购 / 技术 / 商务 / 通用邮箱 / 未知。
- **角色决定口吻与重点**：
  - 决策人 → 只讲商业结果与下一步，不铺技术细节；
  - 采购 → 讲规格可比性、交期、合规文件、试单；
  - 技术 → 讲工况适配、精度、接口、认证，反感空泛销售话术；
  - 通用邮箱（info@ 等）→ 很可能被转呈，务必短、可转发、少附件；
  - 未知或联系人字段是占位值（如「待维护」）→ **不要假装知道对方名字**，称呼用「<公司> team」，
    并把这封信写成「便于转呈、先确认对接人」的形态。
- 系统会在草稿响应的 `brief.role` 里给出判定结果与建议侧重。

### 第 4 步 · 成稿

- 调用 `POST /api/development-email/draft`（`entityType` / `entityId`，可带 `tone` / `goal` / `stage`）。
- **有 AI 就用 AI**：默认 `useAi=true`，走模型撰写（额度不设限）。模型收到的是完整蓝图——
  阶段目标、切入角度、必须包含 / 必须避免、收件人角色与决策权、发件人身份、背调事实与话术线索。
- **没有 AI 或 AI 失败就用固定模板兜底**（`engine` 会标明「按阶段模板」）。固定模板同样按阶段分档，
  并只在背调里**确实出现过**的关键词上做个性化，不会无中生有。

### 第 5 步 · 发送前自检（不得跳过）

草稿响应的 `quality.issues` 是发送前必读的检查项，至少覆盖：

- 正文 / 主题里**出现中文**（收件人看不懂）——英文信里绝不能夹中文；
- 正文里还有未替换的占位符（`[Company name]` / `[Products and services]`）；
- 空泛客套开头（`I hope this email finds you well`）；
- 篇幅超出当前阶段的建议词数；
- **通篇没有一个问句**（收件人没有回复的理由）。

有 `issues` 就先改，改完再发给业务员确认。

### 第 6 步 · 发送与留档

- 真实发送前必须冻结收件人、主题、正文（外部动作确认约束），见 `outreach` Skill。
- 发送成功后回写活动记录，并写入发信台账与触达轨迹；这家客户的开发信过程可在
  「发信明细 → 查看过程」里回看（含发送历史、回复情况、历次背调、过程时间线）。

## 完成标准

- 草稿的 `brief.missing` 为空，或已明确告知业务员缺什么。
- 草稿依据里出现了背调（`brief.researchUsed=true`）或已说明为何没有。
- 阶段判定与信的目标一致；`quality.ok=true`。
- 业务员能在开发信页面直接编辑并发送，无需重写。

## 失败恢复

- **没有背调**：先跑背调；跑不了（未配置 AI / 联网失败）时，用固定模板并把「未背调」如实告知，不要编造事实。
- **没有 AI 模型**：正常回落固定模板，不要卡住流程，也不要提示"功能不可用"。
- **公司资料 / 发件配置缺失**：明确列出缺哪几项并给出去哪里补，不要生成一封注定发不出去的信。
- **阶段禁止发送**：如实说明原因（已拒绝 / 已退信），不要生成草稿让业务员误发。
- **AI 输出夹中文或编造事实**：以 `quality.issues` 为准如实报错，改后重出，不要直接交给业务员。
