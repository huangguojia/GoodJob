# GoodJob CRM 考试系统重构方案与开发手册

## 1. 改造目标

将当前“考试维护和在线答题混在同一页”的功能，重构为企业内部可真实运行的考试闭环：

1. 题库管理员维护题目资产。
2. 考试发布人组卷、设置规则、选择考生并发布。
3. 考生只看到分配给自己的考试任务，在独立答题界面完成考试。
4. 发布人查看参考、缺考、成绩、通过率和补考情况。
5. 已发布考试保留题目与规则口径，答题过程限时、可恢复、可审计。

本次不把“总经理、经理、业务员”写死到考试逻辑中。是否看到管理端由 `training.manage` 决定，是否能参加考试由有效考试指派决定；同一成员同时具备管理权限和考试任务时，可以在“考试管理”和“我的考试”之间切换。

## 2. 现状审计

### 2.1 已有能力

- 基础题库支持单选、多选、类目、标签、难度、解析、导入和导出。
- 考试支持从题库组卷、发布、答题、自动判分和基础报表。
- 接口已有登录鉴权、团队隔离和 `training.read` / `training.manage` 权限检查。

### 2.2 核心缺陷

- 管理者和考生共用同一信息架构，考生会看到题库、发布、团队成绩等无关信息。
- “创建”和“发布”边界不完整，没有正式的发布规则和考生指派。
- 仅有提交记录，没有“未开始、进行中、已交卷、超时交卷”的考试会话。
- 限时只停留在界面文字，没有服务端开考时间和截止时间约束。
- 作答过程不能保存，刷新或网络波动会丢失答案。
- 题目内容引用实时题库，发布后修改题库会影响历史考试口径。
- 报表混合团队数据和个人数据，缺考、参考率、补考资格不清晰。

## 3. 四轮多角色评审

### 第一轮：信息架构之争

**高级产品经理观点**：按功能拆“题库、考试、成绩”即可，所有用户进入同一页，再通过按钮权限隐藏。

**培训负责人反驳**：发布考试是运营任务，关注题库质量、覆盖人员和结果；参加考试是个人任务，关注截止时间、剩余次数和成绩。两者目标完全不同，仅隐藏按钮仍会造成信息噪音。

**资深外贸业务员反驳**：业务员进入 CRM 是为了快速完成任务，不应先理解“当前选中了哪张试卷、右侧是什么统计”。应直接看到“我现在要考什么、什么时候截止、需要多少分”。

**结论**：建立双工作台。具备管理权限者默认进入“考试管理”，普通成员直接进入“我的考试”；有管理权限且被指派考试者可切换视角。

### 第二轮：组卷与发布之争

**高级产品经理观点**：创建考试时直接发布步骤最少。

**考试运营人员反驳**：实际工作中需要先组卷预览，再确定参考人、时间和次数；误发布的成本远高于多一步确认。

**安全工程师补充**：发布后若仍读取实时题库，管理员改答案会改变正在进行或已经完成的考试结果，审计不可成立。

**结论**：采用“草稿组卷 -> 发布配置 -> 发布快照”三段式。创建只生成草稿；发布时校验题量和考生，冻结题目快照及规则。发布后题库修改不影响该场考试。

### 第三轮：答题体验之争

**高级 UI 设计师观点**：答题界面应尽量沉浸，隐藏 CRM 的管理信息，以题目、题号导航、计时和进度为核心。

**资深外贸业务员补充**：外贸人员可能临时接电话或切换页面，答案必须自动保存；交卷前要明确提示未答题数量，不能因误触直接提交。

**考试运营人员提出风险**：允许任意恢复会破坏限时规则，客户端倒计时也可被修改。

**结论**：服务端创建考试会话并计算 `expiresAt`；前端按服务端时间倒计时、答案逐题保存、刷新后恢复。到期由服务端按已保存答案自动交卷。交卷前列出未答题数量并二次确认。

### 第四轮：成绩、复盘与隐私之争

**管理者观点**：需要看到全员答案和错题，便于培训复盘。

**考生观点**：交卷后希望立即知道结果和解析。

**安全工程师反驳**：考试仍开放时立即展示正确答案，会导致答案在团队内传播；普通考生也不得读取他人成绩。

**结论**：管理者可在团队数据范围内查看考试结果；考生仅查看自己的结果。是否显示答案解析由发布规则控制，默认交卷后显示个人得分但不展示标准答案；关闭考试或开启“允许交卷后复盘”后才展示解析。

## 4. 产品结构

### 4.1 考试管理

仅 `training.manage` 可见：

- 运营摘要：草稿、进行中、待参考、平均通过率。
- 考试列表：按状态筛选，显示题量、时间范围、指派人数、参考率。
- 创建考试：填写基础信息并从题库组卷，保存为草稿。
- 发布考试：设置开始时间、截止时间、答题时长、及格分、最大次数、考生范围、是否允许交卷后复盘。
- 考试详情：预览试卷、查看发布规则、关闭考试、查看结果。
- 成绩分析：应考、已考、缺考、通过、未通过、最高分、最近提交时间。

### 4.2 我的考试

所有拥有 `training.read` 的成员可见：

- 待完成：已到开始时间且尚未通过或仍有可用次数。
- 进行中：存在未交卷会话，可继续作答。
- 已完成：展示个人最高分、通过状态和提交次数。
- 未开始/已截止：明确展示原因，不提供无效按钮。
- 独立答题界面：题目区、题号导航、自动保存状态、服务端倒计时、交卷确认。

### 4.3 基础题库

沿用现有独立题库页面，仅 `training.manage` 可进入。题库是可持续维护的资产；考试发布时生成快照，不直接依赖题库实时内容。

## 5. 状态机

### 5.1 考试状态

`draft -> published -> closed`

- `draft`：可修改组卷与规则，不可参加。
- `published`：按开始/截止时间计算“未开始、进行中、已截止”的运行状态。
- `closed`：管理员主动关闭，不允许新开考；已提交结果保留。

旧数据中的 `scheduled` 兼容映射为草稿或待开始状态，不作为新流程写入值。

### 5.2 作答状态

`in_progress -> submitted | auto_submitted`

- 每次点击开始考试生成一次服务端会话。
- 同一考生同一考试只允许一个进行中会话。
- 到达 `expiresAt` 后，任何保存、详情或提交请求都会先触发自动交卷。
- 分数由服务端使用发布快照判定，客户端不提交分数。

### 5.3 指派状态

指派记录保存考生、考试、指派人、次数、最高分和最新状态。考试是否可见以指派记录为准，团队范围发布会在发布时展开为明确成员记录，确保报表分母固定、后续新成员不会意外获得旧考试。

## 6. 数据模型

### 6.1 `exams` 增量字段

- `instructions`：考试说明。
- `start_at` / `end_at`：开放时间。
- `max_attempts`：最多考试次数。
- `allow_review`：交卷后是否展示标准答案与解析。
- `published_at` / `closed_at`：生命周期时间。

### 6.2 `exam_assignments`

- `id`, `exam_id`, `user_id`, `assigned_by_id`, `team_id`
- `status`, `attempt_count`, `best_score`, `latest_attempt_id`
- `created_at`, `updated_at`
- 唯一约束：`exam_id + user_id`

### 6.3 `exam_snapshots`

- `exam_id`, `questions_json`, `rules_json`, `created_at`
- 发布时一次性写入。重新发布草稿可重建；已有作答后不允许替换快照。

### 6.4 `exam_attempts` 增量字段

- `status`, `started_at`, `expires_at`, `updated_at`
- 未交卷时 `score` 仅作为兼容字段，不向考生详情暴露正确答案。

## 7. 接口契约

- `GET /api/exams`：返回当前用户可见考试、个人任务摘要和管理摘要。
- `GET /api/exams/:id/detail`：按身份返回管理详情或无答案的考生详情。
- `POST /api/exams`：创建草稿并组卷。
- `PATCH /api/exams/:id`：修改草稿基础配置和题目。
- `PATCH /api/exams/:id/publish`：校验并发布，创建快照和考生指派。
- `PATCH /api/exams/:id/close`：关闭考试。
- `GET /api/exams/:id/results`：管理者查看团队范围结果。
- `POST /api/exams/:id/start`：创建或恢复当前用户的作答会话。
- `PATCH /api/exam-attempts/:id/answers`：保存当前用户答案。
- `POST /api/exam-attempts/:id/submit`：提交并由服务端判分。
- 保留原 `POST /api/exams/:id/submit` 作为兼容入口，但新界面不再使用。

## 8. 权限与数据隔离

- 题库增删改、创建、发布、关闭、成绩总览：`training.manage`。
- 我的考试、开考、保存答案、交卷、个人结果：`training.read` 且存在本人有效指派。
- 所有查询同时校验 `team_id`；平台运维身份不能通过业务接口读取租户考试数据。
- 尝试记录始终校验 `attempt.userId === session.user.id`，管理结果接口除外。
- 考生接口在允许复盘前剔除 `answerIndex`、`answerIndexes` 和 `explanation`。

## 9. 界面规范

- 管理端：高信息密度、列表优先，避免重复卡片；主要动作为“创建考试”，发布和关闭为行内明确动作。
- 考生端：降低密度，以截止时间、状态、剩余次数和主操作为视觉顺序。
- 答题端：固定题号导航和顶部状态栏；题目内容不因选项变化发生布局跳动。
- 颜色只表达状态：蓝色为主操作，绿色为通过，琥珀为待办/临期，红色为截止/未通过。
- 不在页面堆叠使用说明；必要规则放在考试说明和提交确认中。

## 10. 验收标准

1. 普通考生看不到题库、创建、发布、团队成绩和标准答案。
2. 管理者可创建草稿、选择真实团队成员发布、查看结果并关闭考试。
3. 未被指派的人即使知道考试 ID 也无法读取或开考。
4. 发布后修改题库不影响该考试判分。
5. 开考后刷新页面可恢复答案与倒计时。
6. 超时后不能继续修改，按最后保存答案自动交卷。
7. 达到最大次数后不能再次开考。
8. 团队之间考试、指派和成绩完全隔离。
9. 前端构建、后端构建、考试专项测试和安全回归全部通过。

## 11. 实施顺序

1. 增量迁移数据表并兼容旧考试数据。
2. 完成领域服务与接口，先通过接口级状态机和越权测试。
3. 重构考试首页，按权限渲染管理端或考生端。
4. 重构发布向导和答题界面。
5. 完成构建、专项测试、页面自测后同步个人版。
