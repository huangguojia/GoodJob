# GoodJob CRM 超级搜索模式设计方案

版本：v1.0  
状态：方案审核通过，进入第一阶段开发  
边界：只使用公开或已授权 API、官方开放数据和用户主动导入的数据，不抓取企业网页，不运行浏览器自动化，不绕过登录、验证码、robots 或访问频率限制。

## 1. 产品结论

超级搜索可行，而且适合建立在现有自动获客能力上。它不是“爬更多网页”，而是把一次搜索升级为一个可运行数小时到数天的持久化任务：自动拆分市场和查询矩阵，依次调用允许的数据源，持续去重、清洗、评估覆盖缺口，再生成下一轮搜索计划，直到达到结果目标、覆盖饱和、预算或时间上限。

核心价值：

- 普通搜索解决“现在给我一批候选”，超级搜索解决“把这个市场尽可能系统地找一遍”。
- 每个结果保留来源证据，不把 AI 生成的企业名称当成真实客户。
- 不依赖 AI 也能运行；配置模型后，AI 只增强查询扩展、缺口分析和结果归纳。
- 用户离开页面或服务重启后任务仍可继续，并支持暂停、恢复和取消。
- 所有过滤、去重、失败和未处理结果都可追溯。

## 2. 用户场景

典型指令：

> 在德国、法国和荷兰持续搜索工业泵经销商、系统集成商和水处理工程商，尽量覆盖当地语言表达，目标 500 家，最长运行 24 小时，不使用付费来源。

系统应自动完成：

1. 把产品、应用、买家类型、国家、语言和采购信号拆成查询矩阵。
2. 根据市场与数据能力选择官方企业库、采购公告、通用搜索 API 和已授权商业数据源。
3. 分轮执行、分页检查、记录每个来源有无返回及返回数量。
4. 对企业身份进行归一、跨来源合并、排除已有客户和历史覆盖对象。
5. 展示进入候选、待人工处理和被清洗掉的数据及原因。
6. 根据本轮缺口生成下一轮查询，而不是重复提交同样关键词。
7. 达到停止条件后输出一份完整执行报告。

## 3. 非目标与合规边界

超级搜索不会：

- 下载或解析企业官网页面内容。
- 自动点击搜索引擎网页结果或模拟人工浏览器行为。
- 绕过验证码、账号登录、付费墙、访问频率限制或区域限制。
- 使用未列入数据源目录的任意 URL。
- 把 AI 推测的联系方式、公司名称或采购意向写成事实。
- 无限运行或无限消耗用户的 API、模型和付费数据额度。

允许的数据输入：

- 官方开放 API 和公开数据集 API。
- 用户自行配置且许可范围明确的搜索、企业、采购和联系人数据 API。
- 用户主动上传的官方文件或名单。
- AI 模型产生的查询词、分类和摘要。AI 输出必须由真实来源结果支撑，不能作为企业身份的唯一证据。

## 4. 页面设计

### 4.1 创建任务

在“创建搜客任务”顶部增加分段选择：

- 标准搜索
- 超级搜索

选择超级搜索后仍沿用当前产品关键词、市场、行业、客户类型、排除词和数据源，不再增加大量零碎选项。只增加一个简洁的“搜索强度”区域：

| 配置 | 建议默认值 | 作用 |
| --- | --- | --- |
| 目标候选数 | 300 | 达到目标后进入收敛检查 |
| 最长运行 | 8 小时 | 可选 2 小时、8 小时、24 小时、72 小时 |
| 覆盖深度 | 深度 | 平衡、深度、极限三档，映射到轮数和查询矩阵上限 |
| 费用上限 | 0 | 0 表示只使用免费和用户已有额度的数据源 |
| AI 增强 | 自动 | 有可用模型时启用，无模型时使用规则词典继续运行 |

开始前展示一次搜索计划预览：预计市场单元数、数据源数、最大轮次、最长时间和最高费用。普通免费搜索不增加确认；只有将使用付费来源且费用上限大于 0 时需要明确确认。

### 4.2 任务详情

沿用当前整页任务详情，增加“超级搜索任务”视图：

- 顶部：任务状态、已运行时长、当前轮次、已收获候选、费用、暂停/恢复/停止。
- 第一屏：原始返回、唯一企业、有效候选、待清洗、已过滤五个核心数字。
- 主区域：持续追加的执行流，不覆盖旧内容；显示当前查询单元、数据源请求、分页、返回、归一、去重、入池等细微动作。
- 右侧收获流：最近进入候选池的企业和来源，实时追加。
- 搜索矩阵：按“市场 × 买家类型 × 查询主题 × 数据源”展示待执行、执行中、无返回、返回 N 条、失败、已耗尽。
- 清洗报告：逐阶段输入、输出、去除数量，列出原因和可处理的待清洗记录。
- 失败报告：点击来源或失败步骤查看脱敏后的响应状态、错误码、请求编号、重试次数和建议动作。
- 结束报告：覆盖范围、各轮新增量、重复率、清洗原因、来源贡献、失败来源、未完成项和下一次建议。

界面不使用大段说明文字。说明性信息放在状态、字段名、空态和失败详情中。

## 5. 多轮搜索闭环

每个超级搜索任务执行以下循环：

### 阶段 A：计划生成

根据用户目标生成查询矩阵：

- 产品原词、同义词、型号族和当地语言表达。
- 上游/下游应用场景和终端行业。
- 经销商、进口商、集成商、OEM、EPC、MRO 等买家角色。
- 采购、招标、项目、认证、扩建和供应商注册等业务信号。
- 国家、地区和语言组合。
- 排除词、排除域名和 CRM 已有覆盖对象。

没有 AI 时使用内置行业词典、语言模板和确定性组合器；有 AI 时由模型补充候选词，但必须经过格式校验、去重和规模限制。

### 阶段 B：数据源路由

根据数据源能力和市场选择执行顺序：

1. 企业身份来源：官方企业登记、法人库、行业机构库。
2. 采购信号来源：官方采购、招标、中标和项目数据。
3. Web 搜索 API：只消费 API 返回的结构化标题、摘要和链接，不访问结果网页。
4. 用户授权商业来源：企业、联系人或邮箱发现 API。
5. AI 搜索：只能产出有来源引用的候选或查询建议，不能生成无证据企业。

每个数据源使用目录中的许可策略、速率限制、分页上限、保留策略和当前账号密钥。

### 阶段 C：执行与入账

每次 API 调用都记录请求账本、请求编号、页码/游标、耗时、响应状态、原始数量、无效数量和结算信息。每完成一页即保存检查点，进程退出后从最后一个安全检查点继续。

### 阶段 D：清洗与身份合并

按以下顺序处理：

1. Provider 字段解析与无效记录剔除。
2. 公司名、注册号、域名、地址和国家标准化。
3. 来源内重复和跨来源同一企业合并。
4. 与当前 CRM 客户、线索、候选池和历史搜索覆盖记录比对。
5. 应用排除词、排除域名、区域和 ICP 规则。
6. 评估联系资料完整度和来源证据等级。
7. 合格候选进入候选池；无法完成清洗的记录进入待处理区，不静默丢弃。

### 阶段 E：覆盖缺口分析

每轮结束后按市场、买家类型、查询主题和数据源计算：

- 新增唯一企业数。
- 原始返回到有效候选的转化率。
- 重复率和历史已覆盖率。
- 无返回单元和失败单元。
- 各数据源边际贡献。
- 高价值市场的覆盖缺口。

系统据此生成下一轮：补当地语言、替换买家角色表达、转向采购信号、降低低产出来源优先级，或停止已饱和单元。

### 阶段 F：收敛或继续

满足继续条件才创建下一轮普通搜索运行。每一轮都是可审计、可暂停和可重试的既有 `ProspectSearchRun`，超级搜索任务只负责编排，不绕开原执行内核。

## 6. 自动停止条件

任一硬条件满足即停止：

- 达到最长运行时间。
- 达到用户设定的候选目标并完成最后一轮清洗。
- 达到最大轮次：平衡 4 轮、深度 8 轮、极限 16 轮。
- 达到费用上限、Provider 配额或 AI 调用预算。
- 用户取消任务。
- 所有允许的数据源均不可用或已耗尽。

以下收敛条件连续两轮成立则提前结束：

- 新增唯一企业少于本轮原始返回的 3%。
- 重复和历史已覆盖比例超过 90%。
- 所有未覆盖查询单元都已执行且无新增结果。

单个来源失败不会结束整个任务。系统按错误分类执行退避重试、跳过来源或标记部分成功；认证失败、额度不足和不允许的来源不会无限重试。

## 7. 技术设计

### 7.1 复用现有能力

直接复用：

- `ProspectCampaign` 与版本快照：保存长期搜客目标。
- `ProspectStrategy`：保存查询条件、来源计划和预算。
- `ProspectSearchRun`：执行每一轮搜索。
- `ProspectRunShard`：按数据源执行和展示矩阵状态。
- `ProspectExecutionPage`：分页、游标和检查点。
- Provider 请求账本与原始命中：审计 API 调用和来源数据。
- 候选处理管线：归一、身份合并、覆盖过滤和入池。
- Coverage Memory：避免重复搜索和重复候选。
- Queue Coordinator 与 Worker Service：长时间后台运行、暂停、恢复和取消。
- 当前任务详情的失败报文、清洗报告、待处理导入和实时执行流。

### 7.2 新增编排实体

建议新增三个持久化实体，不把多轮状态塞入单次 Run：

`ProspectSuperSearchMission`

- `id/teamId/ownerId/campaignId/strategyId`
- `status`: queued/running/pause_requested/paused/cancel_requested/cancelled/succeeded/partial_success/failed
- `targetCandidateCount/maxDurationMinutes/depth/maxRounds`
- `costLimit/currency/aiMode`
- `startedAt/deadlineAt/currentRound/totalCost`
- `rawCount/uniqueCount/candidateCount/pendingCount/filteredCount`
- `revision/createdAt/updatedAt`

`ProspectSuperSearchRound`

- `missionId/roundNo/runId`
- `queryPlanSnapshot/coverageBefore/coverageAfter`
- `newUniqueCount/duplicateRate/yieldRate/cost`
- `decision`: continue/converged/limit_reached/manual_stop
- `decisionReason/createdAt/completedAt`

`ProspectQueryCell`

- `missionId/roundNo/market/language/customerType/queryTheme/providerCode`
- `queryText/queryFingerprint/status`
- `rawCount/uniqueCount/candidateCount/duplicateCount`
- `cursor/errorCode/attempts/startedAt/completedAt`

任务事件采用只追加日志，状态更新使用 revision/ETag，避免重复启动和并发覆盖。每个查询单元使用稳定 fingerprint 实现幂等。

### 7.3 API

- `POST /api/prospect-super-search/preview`：预估矩阵、来源、轮次、时间与费用。
- `POST /api/prospect-super-search`：创建任务，用户明确指令即可执行；付费预算大于 0 时冻结预算确认。
- `GET /api/prospect-super-search`：当前账号可见任务列表。
- `GET /api/prospect-super-search/{id}`：任务、轮次、矩阵、报告和事件。
- `POST /api/prospect-super-search/{id}/pause`
- `POST /api/prospect-super-search/{id}/resume`
- `POST /api/prospect-super-search/{id}/cancel`
- `POST /api/prospect-super-search/{id}/process-pending`：任务结束后继续处理待清洗结果。

接口必须加入 Agent 操作契约。读取和免费搜索不额外确认；真实付费、扩大已冻结预算或外部发送仍按风险策略确认。

## 8. AI 的职责与约束

AI 可以：

- 将自然语言目标解析成结构化搜索目标。
- 生成受限数量的同义词、当地语言词和应用场景词。
- 根据上一轮统计做缺口分析和下一轮计划。
- 对有来源证据的字段进行归纳、分类和评分。

AI 不可以：

- 自行增加未授权数据源。
- 自行突破费用、时间、轮数和结果上限。
- 把未由 Provider 返回的信息作为企业事实。
- 读取其他账号的模型密钥、数据源密钥或搜索任务。
- 因模型不可用而阻断整个搜索。模型失败时降级为规则规划器。

模型的每次规划输出必须经过 JSON Schema 校验、Provider allowlist 校验、查询数量上限、预算检查和重复 fingerprint 检查后才能执行。

## 9. 分阶段开发

### 第一阶段：MVP 闭环

- 标准/超级模式切换和五项简洁配置。
- 持久化 Mission、Round、Query Cell 和事件。
- 规则式查询矩阵生成。
- 多轮串行编排、暂停恢复、时间/轮数/结果/费用停止条件。
- 复用当前 Provider、清洗、候选池、失败报文和待处理导入。
- 任务详情展示轮次、矩阵、实时收获和结束报告。

### 第二阶段：AI 增强

- 自然语言目标解析。
- 当地语言和应用场景扩展。
- 基于真实轮次统计的缺口分析。
- 规划输出契约、降级和预算控制。

### 第三阶段：质量优化

- 来源边际产出学习和动态优先级。
- 市场覆盖热力图。
- 历史任务复用与增量搜索。
- 管理员级团队预算、并发与来源策略。

## 10. 验收与 Benchmark

必须建立固定测试集，至少覆盖：

1. 无 AI、全免费来源，任务能完成多轮搜索。
2. AI 已配置但未授权自动获客，正确降级且状态清晰。
3. AI 规划返回非法 Provider、超大矩阵或虚构字段时被拦截。
4. 运行中重启 Worker，任务从检查点继续且不重复入池。
5. 单一 Provider 连续 429，按退避重试后跳过，任务最终部分成功。
6. Provider 401/额度不足，只提示配置问题，不无限重试。
7. 连续两轮新增率低和重复率高，任务自动收敛。
8. 达到费用、时长、轮数和目标数量上限时分别正确停止。
9. 同一企业由三个来源返回，只形成一个企业身份和多条来源证据。
10. 被清洗、待处理和失败的数据均能在详情页定位原因。
11. 用户暂停后不再发起新请求，恢复后从安全检查点继续。
12. 账号之间任务、密钥、查询词、原始结果和候选完全隔离。

验收指标：

- API 来源证据保留率 100%。
- 任务状态可恢复率 100%。
- 已处理记录静默丢失率 0%。
- 查询单元和 Provider 请求可追溯率 100%。
- 同一任务内重复入池率小于 1%。
- 停止条件误触发测试为 0。

## 11. 三视角审核结论

### 高级外贸业务员视角

通过。真正有用的不是“搜得久”，而是市场、客户类型和采购信号有层次，最后能得到可核验、可联系、可继续跟进的候选。方案保留来源证据、联系资料状态、清洗原因和下一轮缺口，符合业务使用方式。

### 高级产品经理视角

通过。入口只增加模式、目标、时长、深度和预算，没有把后台复杂度推给业务员；标准搜索和超级搜索共享结果库与任务详情，避免形成两套割裂产品。建议第一阶段先完成规则式闭环，再启用 AI 自适应规划。

### 合规与可靠性视角

有条件通过。上线前必须完成 Provider allowlist、许可与保留策略、费用硬上限、速率限制、账号隔离、检查点恢复和固定 Benchmark。明确禁止网页抓取、浏览器自动化和 AI 无证据造数后，方案风险可控。

## 12. 审核记录与开发闸门

本方案已完成三方闭环审核：

- 高级程序员：通过。确认复用现有 `ProspectSearchRun` 执行内核，由独立 Mission 编排多轮运行；状态使用 revision/ETag，查询单元使用 fingerprint，Worker 重启后从检查点继续。第一阶段不把 AI 输出直接写入事实数据。
- 高级外贸业务员：通过。确认每轮必须围绕市场、买家角色、应用和采购信号产生可核验候选，并最终落到候选池、线索、跟进和商机入口；清洗和失败结果不能静默消失。
- 高级产品经理：通过。确认普通搜索路径、现有数据源和既有任务详情不受影响；超级模式只新增目标数量、运行时长、深度、费用上限和 AI 增强五项配置，过程页优先展示收获和下一步。

审核闸门：

1. 第一阶段先实现规则式多轮、持久化状态、暂停/恢复/取消、停止条件和执行报告。
2. 所有轮次必须调用现有 Provider/Run/清洗内核，不允许复制一套搜索执行器。
3. AI 查询扩展、缺口分析和动态来源排序属于第二阶段；模型失败时必须自动降级为规则规划器。
4. 第一阶段的 Backend、Frontend、Agent 契约测试和浏览器验收全部通过后，才进入第二阶段。

## 13. 最终建议

可以开发，推荐采用“持久化超级任务编排 + 多轮复用现有搜索运行”的架构。第一阶段不追求一次覆盖所有数据源，先选当前已稳定的官方/公开 API 与搜索 API，完成多轮执行、收敛、清洗报告、暂停恢复和结束报告。只有这条闭环通过 Benchmark 后，再加入 AI 缺口规划和动态来源优先级。

## 14. 第一阶段开发记录

第一阶段 MVP 已完成并通过自测：

- 新增 `ProspectSuperSearchMission`、`ProspectSuperSearchRound` 和任务事件，内存与 MySQL 均可持久化。
