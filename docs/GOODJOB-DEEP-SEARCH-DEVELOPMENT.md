# GoodJob CRM 强化搜索开发文档

版本：v1.0  
状态：技术、产品与外贸业务审核通过，首版实现与 Benchmark 验收完成  
合规边界：仅调用公开或用户已授权 API、官方开放数据及用户导入数据；不抓取网页，不模拟浏览器，不绕过登录、验证码、付费墙或访问限制。

## 1. 产品目标

强化搜索不是让同一条查询重复运行，而是把搜客目标拆成多轮覆盖计划。系统应轮换市场、当地语言、渠道角色、采购信号、工程项目、供应商准入和行业目录等查询主题，每轮复用现有 Provider、请求账本、清洗、身份归一和候选池，直到达到目标、时间、预算、轮次或收敛条件。

验收结果必须能回答四个问题：搜索了什么、每个来源返回多少、哪些结果为何被清洗、下一轮为什么继续或停止。

## 2. 非目标

- 不承诺覆盖整个互联网，也不把模型记忆等同于联网搜索。
- 不将 AI 编造的企业、联系方式或采购意向写成事实。
- 不因未配置模型而阻断标准搜索或超级搜索。
- 不允许模型增加未授权来源、突破预算或跨账号读取配置。
- 不新增需要业务员逐项确认的低风险步骤。

## 3. 职责边界

| 能力 | AI/规划层 | Provider/执行层 |
| --- | --- | --- |
| 理解目标 | 拆解产品、市场、买家角色和采购场景 | 不负责 |
| 查询扩展 | 生成受限同义词、当地语言词和长尾主题 | 接收结构化查询 |
| 事实发现 | 只能提出待核验建议 | 返回来源记录、链接、编号和时间 |
| 企业身份 | 可归纳，不可定案 | 由真实来源和身份归一管线确认 |
| 失败处理 | 分析缺口并生成下一轮 | 按来源独立重试、跳过或失败结算 |

AI 规划失败时必须降级到确定性规划器。单个 Provider 失败只影响该来源，剩余来源继续执行；所有来源失败才允许整轮失败。

## 4. 查询规划契约

每一轮规划输入：审批策略解析后的基础查询、任务编号、轮次、最大轮次、搜索深度、允许的 Provider，以及此前各轮的原始量、候选量、重复率和有效率。

输出包含：

- `resolvedQuery`：本轮实际执行查询，不修改已审批策略。
- `theme`：本轮查询主题。
- `coverageGaps`：依据上轮数据形成的覆盖缺口。
- `queryCells`：市场、语言、买家类型、主题、Provider 和查询文本组成的有界矩阵。
- `fingerprint`：任务、轮次、主题和查询内容的稳定 SHA-256 指纹。

计划写入 Run 的不可变执行快照。公开创建 Run 的接口不能提交该内部字段；只有超级搜索编排器可以生成。数据库保存前校验任务归属、策略归属、轮次范围和计划指纹。

## 5. 多轮主题

前八轮依次覆盖：基础检索、当地语言渠道、采购/RFQ/招标、项目/EPC/工程、进口商/批发商、OEM/集成商、供应商注册、行业协会/目录。极限模式继续覆盖售后 MRO、中标合同、扩产项目、认证生态、区域长尾、应用方案、改造替换和覆盖恢复。

多市场任务按深度分块轮换，单市场任务通过主题与当地表达变化扩大覆盖。`全部`客户类型表现为空约束，绝不作为字面搜索词。

矩阵必须有上限：单轮最多 48 个报告单元、每类查询数组最多 100 项、每个字段长度受持久化 Schema 约束。规划器输出必须确定且可复现。

## 6. 运行闭环

1. 读取审批策略与项目版本，生成本轮计划。
2. 以内部计划覆盖创建不可变 Run 快照，数据源仍来自审批白名单。
3. Worker 按来源执行真实 API 请求，记录请求、分页、响应、失败和费用。
4. 原始记录进入字段校验、身份归一、去重、覆盖抑制和候选池。
5. 轮次结束生成原始量、候选量、重复量、过滤量、待清洗量和来源贡献。
6. 根据覆盖缺口、目标、时间、预算、轮数与连续两轮低收益高重复判断继续或收敛。
7. 页面持续追加轮次主题、查询范围、覆盖缺口、来源结果和清洗报告。

暂停、恢复、取消和服务重启继续使用现有持久化 Mission/Run/Worker 机制。

## 7. 数据与 API 变化

`ProspectRunExecutionSnapshot` 新增可选 `queryPlan`，只对超级搜索存在。`ProspectSuperSearchRound` 新增规划器版本、主题、计划指纹、覆盖缺口和查询矩阵。Round 仍保存在现有 `rounds_json`，本阶段不增加 SQL 表。

现有超级搜索列表与详情 API 自动返回这些字段；标准 Run API 保持兼容。旧任务没有新字段时仍可读取。

## 8. 页面变化

任务详情不增加说明卡片。超级搜索任务直接在现有执行信息中展示：当前轮主题、市场、语言、买家角色、覆盖缺口和本轮矩阵数量。来源成功、无返回、失败报文、清洗报告和待清洗手动导入沿用现有组件。

## 9. 安全与隔离

- 计划只能引用同团队、同负责人、同项目、同审批策略的 Mission。
- 业务员只读自己的任务；管理员只读本团队；超级管理员默认不可进入团队搜客。
- 模型配置和 Provider 凭据保持个人隔离，不写入查询快照或日志。
- 查询计划不能修改 Provider 白名单、费用上限、页数上限和结果上限。
- 日志只保存脱敏错误与请求标识，不保存密钥和完整认证头。

## 10. Benchmark

必须自动验证：

1. 相邻轮次计划不相同，指纹稳定且唯一。
2. 第二轮加入当地语言渠道词，第三轮加入采购、RFQ 或招标信号。
3. 多市场轮换确定且有界，`全部`不成为搜索词。
4. 未配置 AI 时超级搜索和标准搜索均可创建并执行。
5. 单来源失败不阻断其它来源，失败报文可读取。
6. 账号和团队隔离不回退。
7. 暂停恢复、最大轮次停止、连续两轮低收益高重复收敛继续有效。
8. 查询计划通过持久化完整性校验，篡改后拒绝保存。

## 11. 三方审核结论

高级外贸业务员：主题覆盖渠道商、采购、工程、进口、OEM、供应商准入和行业网络，符合真实 B2B 找客户路径；结果仍需来源证据与人工核验，通过。

高级产品经理：沿用现有任务详情、来源报告和清洗报告，没有增加大量配置与确认；用户能看到每轮为何变化和为何停止，通过。

高级程序员：内部覆盖不污染审批策略，计划有稳定指纹、范围上限、租户校验和无 AI 降级；复用现有执行内核，改动边界可控，通过。

- [x] 每个单元记录成功、无结果、部分成功、失败或取消，以及原始量、无效量、重复量、候选量和错误码。

## 14. AI 搜索失败诊断

- `AI_MODEL_REQUEST_REJECTED`：模型返回 400、404 或 422。报告展示脱敏后的上游错误码和正文，并提示检查 Base URL、协议、模型名或不兼容参数。
- `AI_MODEL_RESPONSE_INVALID`：模型请求成功，但返回为空、HTML、非 JSON 或公司 JSON 无法解析。
- GPT-5 与 o 系列默认不发送 `temperature`；其它兼容模型明确拒绝该参数或 system role 时，自动使用兼容请求重试一次。
- Base URL 可以填写 API 根路径，也可以填写完整 `/chat/completions` 或 `/messages` 地址，系统不会重复拼接路径。
- 历史失败请求没有保存原始错误正文，且旧调度器的兜底 HTTP 状态不能证明请求已到达模型，不做原因推断；升级后重新测试配置或重跑来源即可看到真实原因。错误详情始终执行密钥脱敏。
