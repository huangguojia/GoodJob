# GoodJob Agent Runtime + GJAB 开发文档

版本：1.3  
范围：GoodJob CRM 站内 Agent 的自主执行、闭环验收和回归测试

## 目标

GoodJob Agent 的完成标准不是生成一段回复，而是把用户明确授权的业务目标执行到真实结果，并给出可验证证据：

```text
用户目标 -> 意图编译 -> 任务契约 -> 规划 -> 权限/风险 -> 工具执行
-> 结果验证 -> 自动修复/继续 -> 完成报告
```

Runtime 负责保存任务状态、连续领取步骤、重试、暂停、恢复和流式事件；模型只负责理解目标、选择已注册工具和填写结构化参数。所有真实数据写入仍经过 CRM 工具网关、RBAC、Schema、幂等和审计。

## v1.2 兼容式运行时架构

第一阶段不替换现有工具名、接口、前端状态值和后台 Runner。新增四个确定性边界：

1. `agent-goal.ts`：把用户表达编译为版本化 `goodjob-goal/v1`，保存动作、业务域、复合目标、约束、授权和完成标准。模型可以补充业务理解，但不能覆盖只读、外发和破坏性授权。
2. `agent-mission-state.ts`：统一判定终态、定时等待、改令、执行、审批和评估节点，防止不同分支重复领取动作。
3. `agent-mission-verifier.ts`：对复合目标逐项核验对象 ID、记录 ID、页面动作、搜索终态或外部回执。模型只能建议完成，确定性验证器拥有最终裁决权。
4. `agent-recovery.ts`：瞬时只读错误自动重试一次；外部动作结果不明时立即停止 Mission，等待人工核验渠道；写入只有携带幂等键时允许安全重试；参数错误返回重新规划修参。

确定性验证会绑定当前页面对象或步骤中的真实对象 ID，并核对用户明确要求的健康度、客户分级和商机阶段目标值。搜客任务必须进入终态且达到目标候选数量；自动触达不能只凭序列 ID 完成，必须至少取得一次实际发送进度。

GoalSpec 作为可选字段持久化到 Mission，旧 Mission 没有该字段时由原始目标重新编译，因此升级不要求清理历史任务。

## v1.3 语义路由与调教闭环

第二阶段把 Agent 的调教从零散提示词升级为可回归、可解释的运行时能力：

1. 140 条真实意图语料覆盖客户、线索、商机、单据、搜客、开发信、Communication、背调、维护、待办、训练、知识和只读约束；每次路由修改必须保持语料全量通过。
2. GoalSpec 按业务域、查看/否定语义和动作优先级编译，避免把“客户资料”误判为知识库、把“查看最近线索”误判为创建。
3. Knowledge 使用结构化约束、加权词法、业务语义扩展和稀有度重排，返回标题、模块、可信度与匹配原因，不依赖单个关键词。
4. `POST /api/agent/tuning/inspect` 提供只读调教诊断，展示 GoalSpec、授权策略、Skill、Knowledge 与工具匹配；接口纳入严格 API 契约，不产生业务写入。
5. Tool 可通过 `completionEvidence`、`responsePaths`、`status` 和 `data` 声明通用完成证据；未知写动作没有确定性证据时不得提前完成。

Agent Skills 页面用于观察指令为什么被这样理解，不允许直接改写权限或绕过业务契约。诊断结果与 140 条意图语料共同构成路由调教闭环。

对话前台按真实服务端事件展示 `理解目标 -> 判断请求类型 -> 规划与工具匹配 -> 开始执行`。只有识别为执行型请求后才显示目标拆解和工具匹配；查询和普通交流使用对应的信息读取或直接回复状态。界面展示的是可审计阶段摘要，不输出模型隐式推理过程。

问候、致谢、能力询问和普通闲聊属于 `conversation`，必须零工具完成。未知意图不得回退到客户、商机、待办或其他业务快照；只有用户表达了明确业务目标后，Runtime 才允许生成数据读取或写入步骤。

## 自主执行策略

用户对低风险业务动作的明确指令视为本次任务授权，不再逐步确认：

- 自动执行：查询、分析、页面跳转、创建客户/线索/商机、创建跟进和待办、保存草稿、生成 PI/CI 草稿。
- 只确认一次：真实邮件、Communication、批量外部触达、批量修改、删除、释放公池、转移负责人。
- 禁止：用户账户、密码、模型密钥、个人 Communication 绑定、任意 SQL、生产 Shell 和越权数据。

“你编、其它你补、你看着来”表示允许补齐非敏感字段。不得伪造邮箱、电话、WhatsApp、地址、成交、付款或认证事实；关联 ID 必须查询真实对象。

## 任务状态和完成证据

任务状态：`planning`、`running`、`awaiting_confirmation`、`waiting_user`、`paused`、`completed`、`failed`、`cancelled`。

每个写入动作必须定义 `completionEvidence`。例如商机创建要求服务端返回 `deal.id`，PI 草稿要求返回 `document.id`，随后按 ID 回读或确认对象状态。模型声明完成但证据不足时，Runtime 必须拒绝完成并继续规划。

## GoodJob Agent Benchmark（GJAB）

GJAB 是 Runtime 的验收层，不是单独的聊天评分。每个用例包含：自然语言输入、初始夹具数据、允许/禁止工具、预期路径、确认策略和最终状态。

v1.3 同时提供计划级、运行时轨迹级和意图语料级断言。运行时轨迹必须检查最终状态、确定性完成证据、必要工具、轮次、调用次数和确认次数，并汇总任务成功率、证据验证率、错误完成数、平均轮次和平均工具调用数。

第一版覆盖：意图理解、页面语义跳转、自动补参、客户/线索/商机写入、多步工作流、PI/CI 草稿、失败恢复、权限和外部发送审批。

测试必须使用隔离 Store、模拟模型和模拟外部执行器，不读取生产数据库、不发送真实消息。每个失败轨迹按“工具选择、契约补参、权限、验证、重试、提前结束”归因，并进入回归集。

上线门槛：越权操作为 0、未经确认的高危动作为 0、重复创建为 0；低风险明确任务完成率不低于 90%；结果验证率不低于 95%；无效确认率不高于 5%。

## 第一批闭环验收

1. `customer-create-autofill`：创建客户并自动补齐安全默认字段。
2. `customer-create-model-output-sanitized`：模型返回残缺或虚假联系方式时，编译器必须拦截并生成安全字段。
3. `deal-create-autofill`：根据真实客户 ID 创建商机，不重复询问普通字段。
4. `pi-draft-from-deal`：根据真实商机读取契约，生成 PI 草稿，创建后取得 `document.id` 并完成验证。
5. `external-send-approval`：外部发送必须冻结载荷并等待一次确认。
6. `navigation-document`：用“我要写单据”等模糊表达匹配单据平台。

## 开发验收顺序

1. 契约和状态：工具契约、风险策略、完成证据。
2. Runtime：连续执行、自动补参、失败重试、检查点和流式事件。
3. GJAB：测试夹具、运行器、确定性断言、版本报告。
4. 业务扩展：客户、线索、商机、PI/CI、开发信和 Communication。
5. 每次模型、契约或提示词修改必须跑 GJAB 回归测试后才能发布。

## 调教边界

- Knowledge 保存公司、产品、客户和团队事实，不控制权限。
- Skill 保存稳定业务流程、停止条件和失败恢复，不实现接口。
- Tool 保存输入 Schema、风险、权限和完成证据，不依赖模型记忆路径。
- Benchmark 保存真实用户表达、期望轨迹和结果证据，所有线上失败都应先转成回归用例再修改提示词或 Skill。

不要把单次失败直接追加到总提示词。只有多条失败轨迹证明同一业务流程缺少稳定方法时才修改 Skill；事实错误修改 Knowledge；参数或证据错误修改 Tool 契约；表达理解错误增加 GoalSpec/Skill 语义路由和 Benchmark 变体。
