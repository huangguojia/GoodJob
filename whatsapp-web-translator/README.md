# GoodJob WhatsApp 助手（翻译 · 归档 · 自动回复）· Chrome 扩展

在**网页版 WhatsApp**（`web.whatsapp.com`）里做三件事。归档、训练、本地回复全在你自己浏览器里完成，
不经过任何服务器；翻译默认走你自己填的 OpenAI 兼容接口，另可挂一个**免费的机器翻译底座**先把初译显示出来
（这一个会经第三方，默认开、可一键关掉，见「快速底座」）；「CRM 智能回复」可选地接上**本机 CRM**
（回环地址），由本机模型结合客户往来记录出稿。

| 能力 | 一句话 |
|---|---|
| **翻译** | 客户来信自动在气泡下方显示中文译文；你在输入框里打中文会**自动**译成外文，右侧浮框可一键复制 / 一键替换并发送（不用按回车） |
| **归档** | 把对话抓成本地文件（JSONL / WhatsApp TXT / Markdown），TXT 能直接导进 CRM 训练 |
| **自动回复** | 用归档出来的历史对话在本地训练，生成回复；**默认草稿模式**，你确认后才发 |
| **CRM 智能回复** | 把当前会话交给 CRM 那条链路（客户往来 + 报价 + 知识检索 → 本机 CLI 推理出稿）；**只出草稿，不发送** |
| **资料推荐** | 右边整列同时列出「这次该发哪几份资料」，每份给一句可直接发给客户的话；真实链接只在你点「复制链接 / 看正文」时才向本机 CRM 取 |

**右侧整列**：一次给出「推荐回复」（含推荐理由与依据来源）与「相关文档」两块，可折叠成竖条、也可整体关闭；
折叠或关闭后页面宽度完全归还。两个按钮「只要回复（不推资料）」「只要资料（快）」分别走慢通道与快通道 ——
展开面板本身**不会**替你起一个几十秒的模型任务。

前两块与后两块各自加载，一个坏掉不影响另一个。

## 安全边界（先说清楚）

| 做的事 | 不做的事 |
|---|---|
| 读页面上**入站消息**的文字 | ❌ 不改客户发来的消息内容 |
| 在气泡下方**追加**只读译文节点 / 回复建议节点 | ❌ 不碰 WhatsApp 的 socket / 协议 / 加解密 |
| 只在你点「替换到输入框 / 替换并发送」时改写输入框内容 | ❌ 不替你按发送 —— 「替换并发送」发送的只是**你刚点的那一下**（写入验证不过就不发），不会有任何后台自动发送（CRM 那条路更是连发送代码都没有） |
| 调你自己填的翻译接口（OpenAI 兼容） | ❌ 不把聊天记录发往任何**你没填过地址**的服务器 |
| **快速底座**（免费机翻，**默认开、可关**）：只把**待翻的那句话**发给 MyMemory 换一句初译 | ❌ 关掉它之后，除你自己填的翻译接口外不出本机 |
| 在读页面的**本地**做训练与检索（`chrome.storage.local`） | ❌ 不调用任何"训练接口" |
| 归档文件存到你自己电脑的下载目录 | ❌ 不依赖登录态就能用翻译与归档 |
| **只在你点了「用 CRM 生成回复」之后**，才把当前会话发给本机插件，插件按**你的** CRM 权限读该客户名下的跟进 / 报价 / 知识命中 | ❌ 不把 CRM 数据库搬到浏览器里（数据只在插件与 CLI 那边过一遍） |
| 资料推荐里**只给标题、摘要与打分理由**；**只在你点「复制链接 / 看正文」时**才向本机 CRM 取那一份的真实地址或正文 | ❌ 推荐结果里从不含任何链接 —— 页面 DOM 里平时不存在那些地址 |
| **全自动模式**下模拟点击「发送」（默认关闭） | ❌ 不批量群发、不做加好友/拉群等任何主动动作 |

翻译与归档和你**手动**使用网页版 WhatsApp 在协议层完全一样。全自动回复是"模拟人点击发送"，
比非官方客户端（Baileys 那类协议库）风险低得多，但**它确实会自动发出消息** —— 所以出厂默认是草稿模式，
全自动必须你显式选择，并且自带三道闸门（见下）。API Key 只存在本机 `chrome.storage.local`；
CRM 令牌也单独存在那里（`gj_crm_session`），密码**一个字节都不存**。

**接了 CRM 之后边界怎么变**：不用 CRM 时，扩展除翻译接口外不出本机。点了「用 CRM 生成回复」之后，
当前会话（最多最近 20 条）会发给**本机** `127.0.0.1:3100` 上的插件；插件以**你自己的 CRM 身份**去读
**你名下的**数据（`GET /api/customers` 只返回本人客户，WhatsApp 号码字段仅 owner 可见），
再交给本机 CLI 推理。这条路上没有第三方服务器。CRM 与插件地址默认是回环；
改成远端域名时保存会弹一次域名授权 —— 那是你自己填的地址，扩展不会偷偷加。

> 注：清单里除了 `web.whatsapp.com`，还放行了 `http://127.0.0.1/*` 与 `http://localhost/*`。
> 这是留给本地自检（`mock/mock-whatsapp.html`）的，代价是脚本也会注入到你本机的其他本地页面。
> 它只认 `#main` 下两层消息行定位（老类名 `.message-in` / `.message-out`，或改版后的
> `[data-testid="msg-container"]` + `data-id`），在普通页面上不会做任何事；不想要可以在
> `manifest.json` 的 `content_scripts[].matches`、`host_permissions`、`web_accessible_resources[].matches`
> 三处一起删掉那两条（自检脚本会随之失效）。

## 安装

1. Chrome 地址栏打开 `chrome://extensions`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选择本目录 `whatsapp-web-translator/`
4. 首次安装会自动弹出设置页（没弹就点扩展图标 → 设置）

## 配置

### 翻译行为

| 字段 | 默认值 | 说明 |
|---|---|---|
| 自动翻译客户来信 | 开 | 客户发来的外文自动在气泡下方出中文 |
| 译为 | 简体中文 | **入站**翻译的目标语言 |
| 草稿翻译按钮 | 开 | 右下角那个绿色圆形「译」按钮：手动翻一次，任何语言都行 |
| 草稿自动翻译 | 开 | 输入框里打中文 → 停顿约 1 秒自动翻 → 右侧浮框（右上角图标复制 / 替换到输入框 / 替换并发送） |
| 替换后自动发送 | 开 | 浮框里有「替换并发送」一键到底：写入验证过就直接发，不用按回车；关掉则浮框只剩「替换到输入框」 |
| 翻译引擎 | 混合 | 只用机译（最快 · 免费）/ 混合（机译打底 + AI 精修）/ 只用 AI（最准 · 慢）；GJ 面板里也能就地切 |
| 我的回复语言 | 英语 | **出站**中文草稿译成哪种语言 |

### 快速底座（先出初译，不等 AI）

| 字段 | 默认值 | 说明 |
|---|---|---|
| 底座 | `MyMemory（免费 · 无需 Key）` | 选 `关闭` 就回到纯 AI 那条路（也就回到几十秒） |
| 邮箱（可选） | （空） | 填了自己邮箱，MyMemory 的每日额度会放大 10 倍；留空 = 匿名额度 |

**为什么必须有它**：翻译走的那条 AI 线路实测**没有快模型** —— 同一句外贸问句，
最快的 `gpt-5.6-sol` 出首字也要 **10.3 秒**，最慢的 `gpt-5.5` 要 **66.4 秒**。
纯 AI 无论怎么调都追不上"扫一眼就懂"的节奏。所以改成**两段式**：

```
客户来信
  ├─ ① 免费底座（实测 0.8~3.4 秒）→ 立刻在气泡下出译文，标一个琥珀色「机译」角标 + 「AI 精修中…」
  └─ ② 你填的 AI（10~60 秒）→ 回来后**原地替换**成精修译文，角标换回绿色「译」
```

两条刻意加上的约束：

- **机翻永远不进缓存**。只有 AI 精修的结果才写缓存 —— 否则精修失败一次，那句机翻就被**永久钉死在缓存里**，
  以后再也等不到精修。
- **精修只替换气泡下的译文，绝不碰输入框**。它和"你打中文 → 外文"是两件事，后者永远只由你触发。

底座不可用（超时 / 额度用完 / 网络不通）时**不留痕**：直接退回纯 AI，界面上就是以前那个样子。
设置页有「测一次底座」按钮 —— 它**真的发一次网络请求**，≤3 秒算通过。

> 实测数据（2026-10-12，英/西/德/法 六条外贸问句）：**6/6 成功，0.8 ~ 3.4 秒**。
> Google 的免费接口在本机网络下 12 秒超时不可达，`libretranslate.com` 与 `api-free.deepl.com` 均 403 ——
> MyMemory 是实测**无需 Key 且真能用**的那一个。

> ⚠️ **隐私**：开着底座时，**待翻的那句话本身**会发往 MyMemory（第三方）。
> 不接受就把「底座」选成 `关闭`。整段对话、发送人、时间戳**从不外发** —— 出去的只有那一条待翻文本。

### 翻译模型

设置页填四项：

| 字段 | 默认值 | 说明 |
|---|---|---|
| API 地址 | `https://api.52token.org/v1` | 任何 OpenAI 兼容的 `/chat/completions` 服务都行。远程必须 https；本机 `127.0.0.1` 允许 http |
| API Key | （空，需手填） | 就是 CRM 里那个模型用的 Key。**扩展不会去读 CRM 的加密 Key，需要你自己粘一次** |
| 模型 | `gpt-5.6-sol` | ⚠️ **别手输 —— 点右边的「拉取清单」从清单里挑**（见下）。这个默认值是**同一条线路上实测最快的那一个**（首字 10.3 秒），旧默认 `gpt-5.5` 实测首字要 66.4 秒，已被换掉 |
| 推理强度 | 不传 | 可选 `minimal` / `low` / `medium` / `high`。翻译不需要推理，调低能提速 |

#### 模型名一律先「拉取清单」，不要手输

**不同中转站能用的模型差得极远。** 实测某站一共只有 9 个模型、且不含任何 `gpt-4o-*`；
填了 `gpt-4o-mini` 的后果是**每次请求秒回 `404 model_not_found`**，而界面上只显示
「接口路径或模型名不对」—— 表现就是**翻译完全没反应**。

所以点「**拉取清单**」：扩展会直接问接口要一份**模型清单**（`GET /models`），渲染成一排
可以点的标签，**点一下就填进「模型」框**；挑两三个，再用「对比测速」比出谁快。
手输没有意义，只会写错。

> 有的中转站不开放 `/models`（返回 403/404）。那种情况只能手输，提示语会明确告诉你 ——
> 这属于「这条路走不通」，**不是你的 Key 有问题**。

#### 翻译慢怎么办

**绝大多数时候是模型选错了，不是网络问题。** 推理型模型（`gpt-5.x` 这类）在吐译文前会先做
一轮「内部推理」，而翻译不需要推理 —— 实测**同一条线路上**最快的模型首字 10.3 秒、最慢的 66.4 秒，
而且**同一个模型两次跑最多差 3 倍**。按效果排序：

0. **先确认真实数字，再谈优化。** 跑一次 `node tests/live-check.mjs`，它会把这条线路的模型清单、
   你填的模型在不在里面、**真实首字耗时**都报出来。别信设置页那个「5 秒很快」的直觉。
1. **从清单里挑实测最快的那个**（用「对比测速」把候选各测一遍）。这是唯一真正的解法。
2. 把「推理强度」调成 `minimal`（前提是你的接口认这个参数；不认会被 400 拒后自动降级，不会报错）。
3. **接受它快不了，交给快速底座。** 这条线路的物理下限就在 10 秒左右
   （每个请求被固定塞进 3600～4400 `prompt_tokens` 的隐藏前缀，与你写的提示词无关），
   所以默认形态是「底座先出初译、AI 慢慢精修」—— 见上文「快速底座」。

填完点「测试连接」，出现 `N 秒 · … · 译：…` 就通了。保存时浏览器会问一次是否允许访问你填的那个域名 ——
必须允许，否则后台发不出请求。

> 自动回复**不调这个接口**，它走本地历史检索，所以断网、Key 失效时也能用。
>
> 想让它**真的会推理**、并且用上 CRM 里的客户往来与知识库，见下一节。

### CRM 连接（智能回复的前提）

上面那条是"从你自己的历史话术里捞一句最像的"，不联网、不推理。想让它结合**客户跟进历史、
报价记录、知识库命中**再推理出稿，就得把扩展接到 CRM 那条链路上。设置页「CRM 连接」一节：

| 字段 | 默认值 | 说明 |
|---|---|---|
| CRM 地址 | `http://127.0.0.1:4188` | CRM 后端。远程必须 https；`127.0.0.1` 允许 http |
| 插件地址 | `http://127.0.0.1:3100` | WhatsApp 插件（真正跑生成的那一端） |
| CRM 账号 | （空） | 你在 CRM 里登录用的邮箱 |
| 密码 | （空） | **只在点「登录」时用一次，一个字节都不存** |

点「登录 CRM」→ 扩展拿账号换一枚 Bearer（`POST {crm}/api/auth/login`，响应体里就带 `token`；
cookie 是 httpOnly + SameSite=strict，扩展拿不到也带不过去）→ 令牌单独存进 `chrome.storage.local`
的 `gj_crm_session`，**不混进设置对象**（设置会被设置页整块读写，也会进诊断输出）。

「连接状态」那一行会同时报两件事，因为它们是两个不同的失败点：

- **令牌还有多久过期** —— 提前 5 分钟就提示重登，不等你点了按钮白等一轮才报 401
- **插件与本机 CLI 通不通** —— 以及**回复技能（`goodjob-auto-reply`）有没有被扫到**。
  技能没扫到时插件是**静默降档**到话术库的：照样出稿、照样不报错，不点破的话你只会觉得"模型变笨了"。

> 为什么不让扩展自己拼提示词：**"有历史、有推理、有文档搜索"这三样都不在浏览器里** ——
> 客户往来在 CRM 库里，知识检索在 CRM 的 `/api/agent/knowledge/search`（词法检索，
> 见下），推理是本机 WorkBuddy CLI 加载 `goodjob-auto-reply` 技能。
> 扩展的职责只剩"把页面上这段对话读出来交上去，把草稿拿回来"。

**0.6.4 起设置页还有一张「资料推荐效果」卡**（登录后自动出现）：最近 30 天的曝光 / 查看 /
采纳率 / 发送数，以及采纳率最高的几份资料。口径写在代码里：采纳率与发送率的分母都是
「查看」（看到了才谈得上采纳）；拉不到数据时显示原因，**绝不出一张全 0 的假报表**。

### 自动回复

设置页「自动回复（归档 · 训练 · 生成）」一节：

| 字段 | 默认值 | 说明 |
|---|---|---|
| 模式 | **草稿** | `关闭` / `草稿`（生成后填进输入框，你确认再发）/ `全自动发送` |
| 每日发送上限 | 20 | 全自动模式下当天最多发几条 |
| 最小间隔（分钟） | 3 | 两条之间的最短间隔，防手滑连发 |
| 活跃时段 | 8 ~ 22 | 时段外不生成。（起始 = 结束，或两者都为 0 表示全天） |
| 置信度门槛 | 0.72 | 与历史问法的相似度低于此值就不回 |
| 转人工关键词 | （空 = 出厂） | 命中就停止自动回复、页面上标红提醒人工介入 |
| 护栏 | （空 = 出厂） | 出厂 5 条，见下 |

出厂护栏（`src/trainer.js` 的 `DEFAULT_GUARDRAILS`）：

1. 不承诺价格、折扣、交期或库存，除非训练样本或 CRM 数据里有明确依据
2. 不编造公司资质、认证、证书、客户名单或成功案例
3. 不发送合同、付款账户、银行信息或任何敏感财务信息
4. 客户要求转人工、投诉、退款或涉及法律问题时，立即停止自动回复并提醒人工介入
5. 回复保持与训练档案一致的语言和语气，一次不超过 2 条短消息

**护栏只拦机器能判定的硬约束**：第 1 条落地成"回复里出现金额字样（`USD|EUR|CNY|RMB|$|￥|€` 紧跟数字）就拦"。
代价是**含金额的历史原话默认走不了自动通道** —— 这是有意的，避免把过期报价原样发出去。
"是否编造"这类判断机器判定不了，交给草稿模式下的人眼。

## 使用

### 1. 翻译

**入站：客户来信 → 中文**

1. 浏览器里打开 `web.whatsapp.com` 并扫码登录（这就是你平时那个网页会话）
2. 点开任意对话 —— 客户发来的消息会在 1～2 秒内于气泡下方出现译文（带一个绿色「译」角标）
3. 翻译失败时会显示原因和一个「重试」链接

**出站：你打中文 → 外文**

1. 在输入框里打中文，**停一下**（约 1 秒）就会自动翻译，不用点任何按钮
2. 页面**右侧**弹出浮框，标题写着译成了哪种语言（如「译文 · 英语」）
3. 右上角**复制图标**把译文放进剪贴板；底部两个动作按钮：
   - **替换到输入框** —— 输入框里的中文**当场**变成外文，发送由你按回车
   - **替换并发送**（默认显示）—— 写入后**直接发送**，不用按回车。
     写没写进去以读回输入框为准；只有写入被编辑器真正确认过才自动发，发送后再读回确认
     输入框清空了才算发出去，任何一关不成立都照实提示、回车仍在你手里
   - 不想自动发：设置页关掉「替换后自动发送」，浮框里就只剩「替换到输入框」
4. 发送成功浮框亮一下「已发送」然后自动收起；输入框清空（未发送时）浮框也会自动收起，也可点 × 关掉
5. 想翻**英文草稿**（检查自己写的外文对不对）→ 点右下角那个绿色圆形「译」按钮手动触发，
   译文仍是「外文 → 中文」方向

三个刻意加上的约束：

- **只自动翻中文草稿**。你打英文时它不会自动翻 —— 否则输入框会被反复改写，根本没法用。
- **发送只跟着你的点击走**。「替换并发送」发出的只是你刚点的那一下，且有两道闸：
  写入必须被编辑器真正确认（dom 兜底档不自动发）、发送后读回输入框确认清空。
  没有任何后台路径会自己发消息。
- **替换后有约 1.5 秒抑制窗口**。替换本身让输入框从中文变成了外文，不抑制的话自动链路会
  再翻一轮、中↔外来回震荡。

已翻译过的句子会缓存（默认上限 800 条），换会话、刷新页面都不会重复请求。
**缓存里只放 AI 精修过的译文** —— 机翻初稿不缓存，否则精修一旦失败，那句机翻会被永久钉死。

### 2. 归档 + 训练（一条链路）

点扩展图标 →「归档 · 学习」：

| 按钮 | 做什么 |
|---|---|
| 归档并学习（当前会话） | 抓当前打开的会话 → 存训练语料 → 下载归档文件 |
| 归档并学习（全部会话） | 逐个打开左侧会话列表前 50 个（每个约 1 秒），抓完自动切回你原来那个会话 |
| 重学一次 | 用已存的语料重新训练（改了护栏/关键词后点这个） |
| 导出训练包 | 下载 Markdown 训练包：档案摘要 + 标准问答对 + 政策 |
| 清空语料 | 删掉本地语料和档案（归档文件不受影响） |

归档格式三选一：

- **JSONL** —— 与 CRM 插件的 jsonl 导出同字段（`conversationId` / `messages[].role|at|type|content`），一行一个会话
- **WhatsApp TXT（可直接导入 CRM）** —— `[dd/mm/yyyy, hh:mm] 发送人: 正文`，UTC 时间，与插件 `renderWhatsAppText` 同形状
- **Markdown** —— 带统计的完整对白，给人看

**归档文件不经过任何服务器**：直接从页面 DOM 读、直接落进你的下载目录。

**训练在浏览器本地完成**（`src/trainer.js`），流程是：

```
页面 DOM → 归档（含时间戳与发送人）→ 抽问答对与风格样本 → 存本地语料摘要 → 建档案 → 检索 + 护栏 → 生成回复
```

语料摘要只存**问答对 + 风格样本**，不存归档全文（全文可能几 MB，会顶爆 `chrome.storage` 配额，也没必要）。
匹配算法与 CRM 插件 `text-match.ts` 同口径：中文按**相邻两字**切 token、相似度取**较短一侧被覆盖率**、
至少要重合 2 个 token、模板置信度上限 0.9。

### 3. 自动回复

点扩展图标 →「自动回复」→ 选模式。页面右下角会出现一个「归档」悬浮球，点开有面板显示：
当前会话、档案摘要（语气/语言/问答对数）、本地语料量、最近一次决策。

生成回复的三道闸门，**顺序**执行，任一道不过就只标注不发送：

1. **转人工** —— 命中关键词（投诉 / 退款 / 律师 / 起诉 / 假货 / complaint / refund / lawsuit / …）立即停手
2. **时段 / 频次 / 日限额** —— 非活跃时段、距上一条不足最小间隔、当天已达上限
3. **话术匹配 + 护栏** —— 相似度够不够、回复是否触碰护栏

「立即回复最后一条」按钮用于手动触发一次，不看时段和频次（仍看转人工与护栏）。

**草稿模式**下回复会被填进 WhatsApp 输入框，输入框里已有内容时**不覆盖**（那比不填更烦人）。
**全自动模式**下达到置信度就点发送，并把发送计入当日账本。

### 把归档喂给 CRM（可选）

下载的 **WhatsApp TXT** 可以原样丢进 CRM 的「WhatsApp 导入」：
`POST /api/v1/imports/whatsapp-text`（或插件界面里的对应入口）。多条会话用空行分隔，格式与手机导出的一致。

**0.6.4 起有更直接的一条路**：归档并学习完成后，折叠区里会出现「推送到 CRM」按钮 ——
它把**提炼后的训练档案**（风格 + 问答样本 + 护栏，不是会话原文）一键送进插件的训练档案与训练库。
服务端按内容指纹幂等：反复点不会重复入库。需要先登录 CRM；推送失败不影响本地学习结果。

### 4. CRM 智能回复（接了 CRM 才有）

点扩展图标 →「用 CRM 生成回复」，或点页面右下角悬浮球 → 面板里的「用 CRM 生成回复」。走的是：

```
页面读当前会话（最多最近 20 条）
  → background（service worker）
  → 插件 POST /api/v1/auto-chat/compose   ← 用**你这个人的权限**去读 CRM
      ├ 客户档案（按号码优先、其次按名字精确匹配；认不出就不套任何人）
      ├ 跟进记录 / 报价记录（近 8 条跟进、近 6 条报价）
      └ 知识检索命中（近 5 条）
  → 本机 WorkBuddy CLI 加载 goodjob-auto-reply 技能推理出稿
  → 草稿回到面板
```

**一次通常几十秒**（真的在跑本机模型）。所以：

- 从弹窗里点的话，弹窗**可以立刻关掉** —— 生成跑在页面里，关弹窗不会中断，结果落在页面右侧面板
- 面板里那条草稿下面会写清**依据**：命中了哪个客户的几条跟进/几条报价、知识命中了哪几条标题、
  训练库命中多少条。**这是这条链路唯一能被你验证的地方** —— 没有它，"智能回复"和瞎编在你眼里没有区别
- CRM 未匹配到客户时会**如实说"未匹配到客户档案"**，并要求模型**不许编造**客户情况
- 默认带 `cli` 引擎与模型名；超长正文在扩展侧就截断（少传一条比让服务端 400 好，你至少能拿到草稿）

**这条路只出草稿，不替你发送**（`composeFromCrm` 函数体里没有任何发送动作，有测试盯着）。
要发送仍是你自己按回车 —— 错发的报价和承诺撤不回来。

取数任何一步失败都不拖垮生成：CRM 连不上就只丢 CRM 那部分，报价接口 500 就只丢报价，
失败原因收进依据行如实列出（`未取到：报价：HTTP 500`）。

> ⚠️ **"文档搜索"是词法检索，不是向量检索。** CRM 的 `/api/agent/knowledge/search` 走的是
> TF-IDF 加权 + 中文 bigram + 短语命中，响应里自报 `vectorEnabled: false`；全库无 FULLTEXT、
> 无 embedding。所以它按**字面**命中，同义改写（"交期" vs "货期"）不一定搜得到。
>
> **0.6.4 起训练库检索带跨语言词典**：客户用英文问 "MOQ / lead time / price"，库里是
> 中文问答对也能命中（贸易域 20+ 组中英等价词，命中依据会注明「词典等价命中」）。
> 但词典只覆盖高频贸易词——覆盖不到的长尾，还是请把问答对录成客户说的那种语言。

## 什么会被跳过

**入站翻译**

- 你自己发出去的消息（翻译跳过；归档**保留**，训练时只作为"我方回复"样本）
- 已经是中文的消息
- 纯数字（`500`）、纯链接、纯表情
- 客户连发两条一模一样的话 → 只请求一次（同一批并发也会合并）

**出站（草稿）自动翻译**

- 非中文草稿（英文 / 西语 / 日语…）→ 不自动翻，点右下角「译」可以手动翻
- 同一份草稿只请求一次（打字过程中 `input` 事件会连续触发，靠 900ms 停顿 + 原文去重兜住）
- 刚点过「替换到输入框」的 1.5 秒内不再触发（那次内容变化是我们自己造成的，见上文）

## 常见问题

**点了「替换到输入框」，输入框里的内容却没变 / 只说了一句「已替换到输入框」？**

0.6.1 修好了。根因是写入只看 `document.execCommand` 的返回值 —— 而 WhatsApp 的 Lexical 编辑器
会把这次插入**悄悄吞掉或回滚**，命令**照样返回 true**。于是浮框显示「已替换到输入框」、
输入框里一个字都没变。

现在：点一下**当场**替换，成功与否以**读回输入框**为准；一招被吞就自动换下一招
（最后一条是「合成粘贴」，Lexical 认的正是它）；四条路都不通时会照实说
「没能写进输入框，请点右上角复制图标手动粘贴」，**不会**再谎报成功。

**点了没反应 / 不出译文？**

译文是**追加在消息气泡下面**的 —— 页面上原本空着的地方没多出东西，看起来就是"什么都没发生"，
分不清是扩展没装、页面没刷新、消息选择器失效，还是 Key 没填。所以点扩展图标，看「翻译」一节下面的
**自检行**，它直接给出卡在哪一步：

| 自检显示 | 含义 | 怎么办 |
|---|---|---|
| 这一页没有检测到翻译脚本 | 页面里没有我们的脚本 | ① 确认这个标签页是 `web.whatsapp.com`；② **扩展更新或重新加载后，必须按 F5 刷新页面**（旧页面不会自动装上新脚本）；③ `chrome://extensions` 里确认扩展是启用状态 |
| 已接管 · 看到 0 条消息 | 没找到对话区 | 先点开一个具体会话 |
| 已接管 · 看到 N 条，客户发来 0 条 | 认不出消息方向 | WhatsApp 改版了，见「维护」一节 |
| 已显示译文 0 条 · 最近失败：… | 请求发出的但失败了 | 照失败文案处理，多半是下面的 Key / 地址问题 |
| ⚠️ 有 N 条客户消息该翻却没翻 | 请求既没成功也没报错 | 多半是翻译接口不响应：设置页点「测试连接」，看它是几秒返回还是一直转圈 |
| 已显示译文 N 条 | 正常 | —— |

> 不用全靠这张表猜：扩展一旦被重新加载/更新，**页面底部会自己弹出**一条
> 「GoodJob 助手已更新，这一页的翻译已停」并带一个「刷新页面（F5）」按钮 —— 看见它点它就完事了。
> 以前这种状态是静默的（脚本发消息必然失败，于是悄悄停手），用户只能看到"翻译突然不工作了"。

> 要注意：**翻译必须填 API Key**（它是调大模型的），而归档、训练、自动回复完全不调接口，
> 不填 Key 也能用。所以"只有归档能用、翻译不动"是预期行为，补上 Key 即可。

**客户来信一直没有译文（但输入框的草稿翻译正常）？**

0.6.2 给这种「静默停摆」装了**改版哨兵**：聊天开着、面板里明明有消息，但翻译连续两轮扫描
一个消息气泡都没匹配上 —— 页面左下角会自己亮出一条琥珀色横幅：

> 来信翻译没生效：聊天开着，但一个消息气泡都没匹配上 —— WhatsApp 可能改版了。

点「复制诊断」会把一份体检单写进剪贴板（脚本注入 / 行数 / 来信行数 / 改版探针 / 每条消息的
状态与跳过原因 / 最近错误），发给开发者即可定位。在没改版的正常页面上它**不会**出现（有对照断言）。

也可以自己在 WhatsApp 页面按 F12 粘这段看现场（只读，不改任何东西）：

```js
(() => {
  const rows = [...document.querySelectorAll("#main div.message-in, #main div.message-out, #main [data-testid='msg-container']")];
  const isIn = r => r.classList.contains("message-in") || (r.getAttribute("data-id") || "").startsWith("false_");
  const inRows = rows.filter(isIn);
  const stat = {};
  inRows.forEach(r => { const s = r.dataset.gjStatus || "未处理"; stat[s] = (stat[s] || 0) + 1; });
  console.log(JSON.stringify({
    脚本注入: document.documentElement.dataset.gjTranslator || "无",
    消息行总数: rows.length, 来信行数: inRows.length,
    改版探针: document.querySelectorAll('[data-testid="msg-container"]').length,
    状态: stat, 译文节点: document.querySelectorAll(".gj-translation").length
  }, null, 1));
})()
```

**报「翻译超时」或「等了 N 秒一个字都没返回」？**

**头号原因是模型选错了，不是网络问题。** 推理型模型（`gpt-5.x` 这类）在吐译文前会先做
一轮「内部推理」—— 翻译这种轻任务本来不需要。

> 开着「快速底座」时，你其实**不会**看到这句话：初译 1～4 秒就出来了，
> 超时只意味着「精修没回来」，页面上留着的就是那句带琥珀色「机译」角标的初译。
> 底座也关了、AI 也超时，才会看到下面这些失败文案。

「翻译超时」和「API 密钥无效」「连不上翻译接口」是三件事，别混：
超时 = **请求发出去了、上游没回**；密钥错 = 被拒；连不上 = 根本没到对面。

按顺序处置：

1. 设置页点「**拉取清单**」—— 先确认你填的模型**真的在这条线路上**。
   `404 model_not_found` 就是这条：模型名写错了，跟速度快慢无关。
2. 点「**对比测速**」，把清单里的候选各测一遍，看**实际秒数**。
   **超过 8 秒的那个不适合做翻译。**
   > 「模型」框里可以临时放多个名字（逗号隔开，给对比测速用），但**保存前要挑定一个** ——
   > 保存会拒绝一串名字；就算漏进请求层也会被就地拦下，绝不会有 `model: "a,b,c"` 这种请求发出去。
   > 这条守卫是真实教训换来的：曾经整串被当成一个模型名发往上游，换回 404 还查不到原因。
3. 若你的接口认 `reasoning_effort`，把设置页的「**推理强度**」调成 `minimal`；
   不认也没关系 —— 会**自动去掉该参数重试一次**，不会因此报错。
4. 「**首字超时**」是一道闸：默认 **60 秒**还没吐第一个字就判死并建议你换模型，而不是干等。
   **它不重试** —— 重试还是同一个模型。
   > 这个值曾是 8 秒，直接**把所有模型全部击穿**（这条线路最快也要 10.3 秒）—— 表症就是「翻译永远不出」。
   > 现在旧配置会在打开设置页时被**一次性迁移**到 60 秒 / 120 秒，不用自己改。
5. 客户来信遇到**整体超时**会**自动重试一次**；草稿翻译**不重试** —— 你正盯着浮框，宁可早点告诉你。
6. 浮框在失败时会多出一个「**重试**」按钮（以前那一刻两个按钮都是灰的，只能干等）。
7. 万一某条消息连失败提示都没有：45 秒后它会被**自动捡回来重译**。以前这种情况会**永久沉默** ——
   页面上既没有译文也没有报错，一条客户消息可以空十几个小时。

**翻译报「API 密钥无效」**：Key 填错或过期，去设置页重填。
**报「接口路径或模型名不对(404)」**：**先点「拉取清单」核对模型名** —— 这是最常见的原因
（模型名写了个这条线路上不存在的）；地址填到 `/v1` 即可，扩展会自己补 `/chat/completions`。
**报「远程 API 地址必须用 https」**：故意加的限制，明文远程端点不接受（本机 `127.0.0.1` 例外，方便自测）。
**报「还没配置翻译模型」**：设置页三项（地址 / Key / 模型名）里还有空的。

**自动回复说「未回复：没有匹配到话术」？**
语料还不够 —— 先「归档并学习（全部会话）」，问答对攒到几十组后命中率才上来。也看面板里的问答对数量。

**点了「用 CRM 生成回复」没反应 / 报连不上？**

这条链路有三个独立的失败点，先看**设置页「CRM 连接」的连接状态行**，它把三个都报出来了：

| 状态行说什么 | 卡在哪 | 怎么办 |
|---|---|---|
| 未登录（智能回复现在用不了） | 没换到 Bearer | 填 CRM 账号密码 → 点「登录 CRM」 |
| 登录已过期 | 令牌到点了 | 重新登录一次（提前 5 分钟就会提示，不会等你点了才报 401） |
| 本机 CLI 不可用：… | 插件在，但 `codebuddy` 跑不起来 | 照原因处理；`codebuddy` 没 `/login` 也会"跑得起来但没结果" |
| 技能 `goodjob-auto-reply` 没扫到 | **静默降档**：还能出稿，但走的是话术库不是模型 | 把技能放进插件的 `skills/` 目录，然后**重启 Runner** |
| 连不上插件（`http://127.0.0.1:3100`） | 插件没起 | 先把插件跑起来；端口不对就改上面的「插件地址」 |

**等很久是正常的** —— 这是真的在本机跑一次模型推理，几十秒是常态。从弹窗点的话弹窗可以直接关掉，
生成跑在页面里，结果会落在页面右侧面板。

**回复里写「CRM 未匹配到客户档案」？**
按号码优先、其次按名字**精确**匹配，都不中就**不套任何人**（刻意不做模糊匹配：套错客户的报价历史比不套更危险）。
检查 CRM 里这个客户的 WhatsApp 号码是否与页面上的一致（归一化只处理 `+`/空格/横线/括号，不猜国家码）。

**"文档搜索"搜不到我想要的？**
它是**词法检索**（TF-IDF + 中文 bigram + 短语命中），不是向量检索 —— 按字面命中，
同义改写（"交期" vs "货期"）不一定搜得到。想加强就先在 CRM 知识库里把常见说法都写进去。

**自动回复说「可能触碰护栏」？**
历史原话里有金额（`$`/`€`/`￥` 紧跟数字）。想放行就把设置页的护栏清空（留空 = 用出厂，不是关闭；要关得改 `trainer.js` 的出厂值）。

**归档下载的文件是空的 / 只有几行？**
WhatsApp 会虚拟化长列表，只渲染可视区域那几十条。先在对话里向上滚到你想归档的位置，再点归档。

**归档时左侧会话列表没动？**
「全部会话」会逐个点击左侧会话并等待切换（按 `data-id` 判断）。抓完会切回你原来打开的会话，最多 50 个。

**自动回复会不会因为我用了就被封号？**
它只是模拟"页面里有个人点了一下发送"，不碰协议、不碰 socket，和你自己点发送在协议层没有区别。
但**它确实会在你不看着的时候发出消息**，所以：出厂默认草稿模式；要用全自动就配上日限额、最小间隔、
活跃时段和转人工关键词。真正会招来风控的是"同一时间大量群发"，那不是这个扩展做的事。

### 几个刻意为之的设计

- **「替换到输入框」的成功与否，只认"读回输入框"这一个判据。** WhatsApp 的输入框是 Lexical 编辑器，
  两个坑叠在一起：① 只改 DOM 不会同步到它内部状态 —— 字看起来填进去了、按回车却发不出去，
  所以必须走编辑命令；② 反过来，编辑器也可以把编辑命令**悄悄吞掉或回滚**，而
  `document.execCommand` **照样返回 true** —— 只看返回值就会显示「已替换到输入框」、输入框一个字没变。
  做法：排四招（整段选中 + `insertText` → 编辑器自己的 `selectAll` + `insertText` → **合成一次粘贴**
  （Lexical 认的正是这条）→ 直接写 DOM + 派发 `input`），**每一招都读回输入框比对**，一招不成换下一招；
  四招都不成立就照实报"没能写进输入框"并让人去「一键复制」——**绝不谎报成功**。
  写入是异步的：要先让出一帧（Lexical 靠 `selectionchange` 异步同步选区），同步立刻插会撞在它的旧选区上。
  这段实现在 `src/content.js` 与 `src/autoreply.js` 里**各存一份**（content script 不能用 ESM），
  由 `tests/parity.test.mjs` 逐字比对，改一处必须同步另一处。
- **多行正文必须保住换行**。归档正文用 `normalizeMessageBody`（只折叠行内空白、保留 `\n`），不能用
  `normalizeBody`（把 `\n` 也压掉）—— 否则客户写的「1) … 2) …」在归档里会糊成一坨，
  而插件的 TXT 解析器本来就会把没有时间戳前缀的行并回上一条正文，多行是能往返的。
- **日月顺序只在能确定时才敢确定**。`parsePrePlainText` 只在第一位 >12 或第二位 >12 时才判 `dmy`/`mdy`，
  两个都 ≤12 就用默认 `dmy`（与插件同口径）。猜错会把 `10/11` 变成 11 月 10 日。
- **护栏失败要"静默降档"而不是报错**。任何一道闸门不过都返回 `skip` + 可读原因，页面上标灰，绝不抛异常打断页面。
- **训练档案里不含归档全文**。见上文语料摘要层。

## 视觉与品牌标识

整套界面只有**一处**样式来源：`src/gj-theme.css`。它同时被注入 WhatsApp 页面的两个 content script
和扩展自己的 popup / options 引用 —— 拆成两份必然漂移，所以只有一份。

- **设计令牌取自仓库里既有的 GoodJob 设计系统**，不另发明：
  颜色 / 圆角 / 阴影 / 缓动 抄自 `whatsapp-plugin/src/web/styles.css` 的 `:root`；
  GJ 标识的几何与配色抄自 `frontend/index.html` 的 `.brand-mark`（默认主题「晨白 Paper」）。
- **品牌色是 `--gj-brand: #6366f1`**（CRM 默认主题的品牌色）。扩展此前一处用 `#1d9e75`（绿）、
  一处用 `#4f46e5`（靛），同一个产品两副面孔；现在收成一处，`parity.test.mjs` 会盯着注入样式里
  不许再出现旧色值。
- **GJ 标识**（`.gj-mark`）= 品牌浅底圆角方块 + 深色「G」与品牌色「J」错位并排 + 右下角品牌短条，
  与 CRM 侧栏的品牌标完全同构。几何按参照的 42px 基准**等比换算**，所以从 20px 的浮框页头到 38px
  的设置页头都是同一个标。用在：设置页/弹窗页头、归档面板页头、译文浮框页头、归档/学习的悬浮入口。
- **扩展图标** `icons/icon-{16,32,48,128}.png` 从同一份几何绘制，矢量源是 `icons/icon.svg`
  （坐标直接用 42px 基准刻度，每个数字都能在上游 CSS 里找到对应）。16px 那一枚按图标惯例
  **简化为单个「G」+ 短条** —— 两个字母并排在 16px 里必然糊成一团。
- 悬浮入口有两颗：上面那颗是 **GJ 标识**（开归档/学习/自动回复面板），下面那颗是**品牌实心方块 +
  「译」字**（翻草稿）。同尺寸、同圆角、同阴影，同一族但一眼能分清"哪个是标、哪个是键"。

### 有意保留的偏离（都在注释里写了原因）

- **多做了暗色档**。参照的插件样式只做浅色 —— 它以 iframe 挂在浅色 CRM 里。但本扩展的宿主是
  WhatsApp 网页版，用户开暗色是常态，一块纯白浮框压在暗色聊天窗上会比"没有暗色"更难看。
  暗色档全部由同一批令牌名派生，不引入新色相。
  > ⚠️ 跟随的是**系统**的 `prefers-color-scheme`，不是 WhatsApp 自己的主题设置。macOS 开暗色、
  > WhatsApp 又手动选了浅色主题时，浮层会比聊天窗深一档。
- **语义色上的文字另立令牌**（`--gj-on-green` / `--gj-on-danger`）。暗色档语义色被提亮，
  沿用白字会掉到 2:1 对比度，所以"红底/绿底上写什么字"收成令牌而不是在组件里手写 `#fff`。
- **开关轨道**（`--gj-track`）由 `--gj-muted` + `--gj-surface` 派生。参照只给了浅色的 `#b8c0bc`，
  照抄到暗色档就是"深色轨道压深色卡片"，关态看不出来。

### 真实链路自检（`tests/live-check.mjs`）

上面那些全是**桩**：单测注入假 `fetchImpl`，e2e 打本地 mock。它们能证明「逻辑分支对」，
但**在结构上**看不见任何真实世界的事实 —— 地址通不通、Key 有没有权限、**模型名在这条线路上
到底存不存在**、真实要跑几秒。

这个盲区真实伤过一次：扩展里被填了该线路根本没有的模型名（`gpt-4o-mini`），于是每次请求秒回
`404 model_not_found`，而当时**776 项单测（其中 parity 243 项）+ 128 项端到端全绿** —— 用户那边
一条译文都出不来，界面上也没有任何线索。所以这一层单独拆出来，只做一件事：**把真实链路跑一遍，
并说出真实数字。**

它还会**主动报出阈值矛盾**：比如「你的首字预算只有 8 秒，而这条线路最慢的模型首字要 66 秒」——
这种"能翻但会被自家超时掐死"的自相矛盾，只有这里看得见（后来就是这么找出用户的翻译为什么一直不出的）。

```bash
node tests/live-check.mjs
```

配置来源按优先级：`GJ_API_BASE` / `GJ_API_KEY` / `GJ_MODEL` 环境变量 → 本机 Chrome 里扩展的
实际设置（读 `chrome.storage.local`）→ 都没有就 SKIP（退出码 0，**不算失败**）。

它报四件事：这条线路**有哪些模型**、**你填的模型在不在里面**、真实翻译耗时、
以及**耗时有没有已经贴近自家超时线**（"能翻但会被自家超时掐死"这种自相矛盾，只有这里看得见）。

> `parity.test.mjs` 存在的原因：content script 不能用 ESM，所以 `isChineseText` / `isTranslatable` /
> `hasWord` / `detectLanguage` / `draftTarget` / `shouldAutoTranslate` 在 `settings.js` 与 `content.js`
> 里**各存一份**。这个"两份"真实出过问题 —— 改了前者忘了后者，页面行为没变而单测全绿。现在它会
> 把两份抠出来（去注释与空白后）逐字比对，忘同步就是一条红的测试。它同时校验 `manifest.json`
> 引用的文件（含四个图标）都在、所有 ESM 相对导入都能落到磁盘上，以及**设计令牌的一致性**：
> `content_scripts[].css` 第一项必须是 `gj-theme.css`、四个界面文件里 `var(--gj-*)` 引到的名字都
> 在 `gj-theme.css` 里有定义（拼错令牌会静默失效，比写错色值更难查）、注入样式里不许再出现旧品牌色
> `#1d9e75` / `#4f46e5`。
>
> 它还盯住 **CRM 通道的接线**：设置页/弹窗里 `el("x")` 引的 id 必须真在对应 HTML 里（拼错一个就是
> 整页 TypeError）、各处从 `crm.js` import 的名字必须真被导出、页面与弹窗发出去的每个 CRM 指令
> background 都必须有分支（少一个是"点了没反应"）、以及 `composeFromCrm` 的函数体里**不许出现
> 任何发送动作**（这条路只出草稿）。
>
> `crm.test.mjs` 用桩替换 `fetch`，断言比的是**实际发出去的请求**而不是返回值。为什么必须这样：
> 地址嵌在 `settings.crm` 下，曾经被读成 `settings.crmBaseUrl` —— 取到的永远是 `undefined`，
> 于是**静默回落到回环默认值**，用户填了远端地址也连不上、还不报任何错。只看返回值的话，
> "回落到了一个同样合法的默认地址"这件事根本测不出来。

> ⚠️ 本机踩到的三个环境坑，下次别再绕（自检脚本里都写了注释）：
> 1. 这份 Chrome 在 `--headless=new` + `--load-extension` 下**不注入 content script**（用最小扩展单独复现过：`<all_urls>` 也不注入，SW 却正常）。所以自检脚本第二段用 http 把**同一份** `content.js` / `agent.js` 加载进页面来验，绕开坏掉的注入通道。
> 2. 扩展上下文（service worker 和扩展页面都一样）发起的 **HTTP 请求会永久挂起**，同一个 URL 在普通页面里却正常。所以"真 SW 打真接口"这条在本机只能跳过。
> 3. 一旦给 Chrome 指定自定义 `--user-data-dir`，**http(s) 导航会永久卡住**；用 `Target.createTarget` 新建标签再导航 http 也会卡。必须用 `Page.navigate` 导航启动时就存在的页面 target。
> 4. **Google Chrome 稳定版 154 起忽略 `--load-extension`**（153 及以下的 Chrome for Testing 正常）。症状是扩展压根不加载、`Target.getTargets` 里连 service worker 都没有。所以 `CHROME_SHELL` 要指 Chrome for Testing ≤153，见上面的「测试」一节。
